# 内容产品扩展研究报告

日期：2026-07-16

> **状态说明：探索性候选报告。** 本文保留早期“先做《道德经》”的验证思路，供比较
> 产品边界与复用成本；正式产品顺序已由后续
> [`MAHAYANA_PRODUCT_PLANS.md`](MAHAYANA_PRODUCT_PLANS.md) 取代，当前主线为
> 《金刚经》→《圆觉经》→《六祖坛经》。不要把本文末尾的早期排序当作实施指令。

## 结论先行

这套 app 最适合扩展成“经典深读/听读/每日一句”类产品，而不是普通电子书阅读器。它的强项不是书架、购买、社交，而是：

- 树状目录与章节路径：适合有章句、品、卷、科判、篇目的经典文本。
- 沉浸长文阅读：适合需要慢读、反复读、背诵或查找的文本。
- 听读音频：适合诵读、通勤学习、长辈使用。
- 收藏、精选、每日经文、提醒、Widget：适合“每天接触一点”的内容。
- 分享图与文字分享：适合短句传播、朋友圈/微信场景。
- 本地隐私、无账号、无广告调性：适合宗教、修身、古籍学习类内容。

用户提到的《论语》《金刚经》《道德经》都适合，但优先级不一样：

1. 《道德经》最适合做第一款非佛教验证版：文本短、81章天然结构、每日一句/分享/Widget 价值很高，数据迁移成本最低。
2. 《金刚经》最适合从当前楞严用户群横向扩展：同属佛经读诵场景，音频、分享、提醒、庄严视觉都可复用。
3. 《论语》大众学习价值最大，但不能只做原文阅读；需要译文、注释、主题标签或学习卡，否则用户价值不如已有免费文本网站。

我的建议：先做《道德经》和《金刚经/心经》两个小单品验证，再抽象 `BookConfig` 做多书平台；不要直接把当前代码改成大而全的“古籍库”。

## 当前 App 可复用能力

仓库证据：

- 架构文档：`.planning/codebase/ARCHITECTURE.md` 定义了 UIKit/SwiftUI 混合架构，核心为 `Book.shared`、`AudioManager.shared`、`Prefers.shared` 和 Design System。
- 数据结构：`SUTRA_DATA_STRUCTURE.md` 描述了 `index-tree`、`index`、`content`、`media`、`chapter-map` 四类 JSON，天然适合迁移到其他经典。
- 实际数据规模：
  - `lengyanjing-index.json`：1669 个目录/索引节点。
  - `lengyanjing-content.json`：1155 个正文路径，1262 段正文，约 76049 个经文字。
  - `lengyanjing-media.json`：11 个音频条目。
  - `lengyanjing-chapter-map.json`：10 卷映射。
  - 数据包约 1-2MB，音频资源约 368MB。
- 已有产品能力：
  - `SearchService.swift`：科判标题 + 正文全文搜索。
  - `DailyVerseProvider.swift`：每日内容池、收藏混合、Widget 同步。
  - `ReminderManager.swift`：本地每日提醒。
  - `ModernFavoritesView.swift`：个人收藏 + 精选内容。
  - `SutraCardRenderer.swift`：分享图、长图分页、文字导出。
  - `AudioManager.swift`：ODR 音频下载、播放、断点状态。
  - `LengyanWidget/DailyVerseWidget.swift`：小/中/大桌面组件与锁屏组件。

这说明它已经是“单本经典学习引擎”，不是只能承载《楞严经》。

## 当前迁移阻力

数据层可迁移，但产品层仍有较多《楞严经》硬编码：

- `Book.swift` 写死加载 `lengyanjing-index-tree/content/index/media/chapter-map`。
- `Constants.swift` 写死 `KEY_PATHS` 和 `DEFAULT_STARTS`，这些是楞严科判路径。
- `SutraFrontViewController.swift` 有 10 卷按钮、楞严经题、礼敬文案、路径逻辑。
- `DailyVerseWidget.swift`、本地化字符串、App Store 元数据、URL scheme、Bundle ID 都围绕楞严。
- 音频 ODR tag 当前是 `ly01` 到 `ly10` 等楞严资源。

因此现在更适合“复制代码做单书 App”或“先轻量抽象再做系列”，不适合立刻在一个 app 内上很多书。

## 用户价值分层

### 1. 佛经读诵类

适合书目：《金刚经》《心经》《阿弥陀经》《地藏经》《普门品》《六祖坛经》。

核心用户价值：

- 每日定课：提醒 + Widget + 上次进度。
- 跟读/听经：音频是刚需，尤其对长辈和通勤场景。
- 庄严阅读：当前宣纸、古籍、暗色主题可直接复用。
- 分享法语：分享图比普通复制更有传播价值。

产品形态：

- 单本：《金刚经》《地藏经》。
- 小合集：《般若经典：心经 + 金刚经》《净土常诵：阿弥陀经 + 普门品》。
- 长期系列：与《楞严》形成同一品牌下的“佛经深读”系列。

注意：

- 佛教文本原典多为古籍，但数字校勘版本、标点、音频录制都有独立版权或使用条款。CBETA 官方说明其目标是免费提供电子佛典；其具体文本/电子书常见非营利或流通限制，App Store 商用、广告、内购前必须逐条确认。

### 2. 儒家/国学学习类

适合书目：《论语》《孟子》《大学》《中庸》《孝经》。

核心用户价值：

- 每日一句：适合家庭教育、学生、职场自省。
- 章句深读：按篇章和章句进入，收藏重要句子。
- 搜索引用：用户经常记得一句话但忘记出处。
- 白话理解：学习价值主要来自“原文 + 注释 + 译文 + 主题”。

产品形态：

- 单本 MVP：《论语》。
- 系列升级：《四书》。
- 学习版增强：按主题组织，如“仁、礼、学、政、孝、君子”。

注意：

- 只放原文不足以形成明显价值；因为很多网站已经能免费查看原文。
- 要做得有价值，至少要支持第二层内容类型：`original`、`translation`、`annotation`、`note` 或 `commentary`。

### 3. 道家/修身哲学类

适合书目：《道德经》《庄子》《列子》。

核心用户价值：

- 短章反复读：尤其适合 Widget、提醒和分享。
- 静心产品定位：比“学习工具”更贴近当前 app 的宁静气质。
- 低数据成本：道德经 81 章，结构简单，适合快速验证。

产品形态：

- 单本：《道德经》。
- 后续：《庄子》分内篇/外篇/杂篇，需要更多注释。

注意：

- 《道德经》原文短，必须通过排版、音频、注释、每日卡片、收藏回顾来提高留存。

### 4. 策略/管理类经典

适合书目：《孙子兵法》《三十六计》。

核心用户价值：

- 非宗教受众更广，商业化空间更大。
- 每日一策、收藏、分享都适配。
- 搜索和主题标签很重要。

产品形态：

- 《孙子兵法》先行，13 篇结构简单。
- 可增加现代案例，但案例文本需要原创或授权。

注意：

- 当前禅意审美可以复用一部分，但文案和视觉需要从“经书庄严”转成“古籍策略/冷静学习”，不能照搬佛经语境。

## 外部内容与授权参考

- Project Gutenberg 的《The Analects of Confucius》页面标明 “Public domain in the USA”，并提供多种下载格式；这适合用来评估英文公版译本和国际化方向。链接：https://www.gutenberg.org/ebooks/3330
- Project Gutenberg Confucius 作者页也有中文《論語》等条目，可作为候选底本线索。链接：https://www.gutenberg.org/ebooks/author/1180
- Chinese Text Project 提供《论语》《道德经》等古籍的在线浏览、搜索和 API 文档，是非常好的校对/结构参考；但用于 app 内置前仍应确认其使用条款。链接：https://ctext.org/analects 、https://ctext.org/dao-de-jing 、https://ctext.org/tools/api
- CBETA Online 有《金刚经》《心经》《法华经》等佛典在线阅读；适合作为佛经数据和结构参考，但商业使用必须单独确认授权。链接：https://cbetaonline.dila.edu.tw/T0235 、https://cbetaonline.dila.edu.tw/T0251 、https://cbetaonline.dila.edu.tw/T0262

原则：古籍“原文”通常已进入公版，但“数字校勘文本、现代标点、白话译文、注释、音频、排版 PDF、数据库导出”可能仍受版权或使用条款限制。我们应优先选择可明确商用/可再发布的来源，或自己整理校对。

## 技术路线建议

### 方案 A：快速单品复制

适合：《道德经》《金刚经》。

做法：

- 复制当前 app，替换数据 JSON、音频、App 名称、Widget 文案、App Store 元数据、图标和分享水印。
- 保持单本书体验，不引入书架。
- 每本书做单独 Bundle ID 和 URL scheme。

优点：

- 改动最少，最快能验证用户需求。
- 不会破坏当前《楞严》稳定性。

缺点：

- 多本书会产生维护重复。
- 每个新 app 都要处理硬编码替换。

预估：

- 无音频短书：数据准备后 2-4 天可出可测版本。
- 有音频、Widget、App Store 全套：1-2 周。

### 方案 B：抽象 BookConfig 后做系列

适合：计划持续做 3 本以上。

新增一个 `BookConfig`/`BookManifest`：

```json
{
  "bookId": "daodejing",
  "title": "道德經",
  "shortTitle": "道德經",
  "watermark": "道德",
  "dataPrefix": "daodejing",
  "chapterCount": 81,
  "navigationMode": "chapter",
  "featuredPaths": [],
  "audioCredit": "",
  "widgetHeader": "道德經",
  "homageText": "",
  "urlScheme": "daodejing"
}
```

需要改：

- `Book.swift` 从 manifest 加载数据文件，不再写死 `lengyanjing-*`。
- `KEY_PATHS` 从目录树或 manifest 生成，不再硬编码。
- `DEFAULT_STARTS` 放进 manifest，作为每日内容池/精选内容。
- 首页标题、礼敬文案、卷章按钮数、Widget 文案、分享水印全部来自配置。
- 音频 ODR tag 由 `media.json`/manifest 控制。
- 增加数据校验脚本：检查 index、tree、content、chapter-map、featuredPaths 是否互相一致。

优点：

- 第三本之后效率明显提升。
- 可以做同一代码库多个 target，或者一个 app 内多书。

缺点：

- 初期改动较大，容易影响现有楞严。

预估：

- BookConfig 基础抽象：2-4 周。
- 后续每本书：数据准备后 2-5 天接入。

### 方案 C：多书大平台

暂不建议现在做。

原因：

- 当前产品气质是一本书的沉浸体验，不是书库。
- 多书平台会引入书架、下载管理、跨书搜索、分类、版权、更新、体积管理。
- 这些会稀释现有“打开即读”的核心价值。

## 推荐路线图

### 第 1 步：做《道德经》原型

目标：验证非佛教经典是否吃当前阅读/Widget/分享模型。

范围：

- 81 章原文。
- 每日一句/Widget/收藏/分享。
- 暂不做复杂注释，可先做简短章题或主题标签。
- 可无音频先验证阅读和分享。

成功标准：

- 用户每天能通过 Widget 接触一章/一句。
- 分享图效果自然，不像佛经换皮。
- 首页不需要十卷结构，81 章导航能清楚可扫。

### 第 2 步：做《金刚经 + 心经》佛经扩展

目标：验证当前楞严用户是否愿意接受同品牌佛经系列。

范围：

- 《金刚经》按传统分品/段落组织。
- 《心经》作为短经加入，不单独成 app。
- 优先找可用音频；没有音频则先纯阅读。
- 分享图、每日提醒、Widget 全开。

成功标准：

- 佛经场景完全复用当前调性。
- 数据规模远小于楞严，打开分享/搜索/Widget 应更稳。

### 第 3 步：为《论语》补学习层

目标：从“读经/读典”进入“学习经典”。

必须补：

- 原文 + 白话译文 + 注释三层结构。
- 按篇章/章句导航。
- 主题标签：学、仁、礼、孝、政、君子、朋友等。
- 搜索结果显示原文与译文。

成功标准：

- 用户不是只读原文，而是能理解、收藏、复习、引用。
- 每日一句能直接进入对应章句深读。

## 不建议现在做的方向

- 不建议立刻做“大藏经/四库全书/全古籍平台”。当前架构是单书深读，不是海量资料库。
- 不建议先做《易经》。它需要卦象、爻位、象传、彖传、占筮/解释等独立交互，不是简单树状长文。
- 不建议直接使用现代译本、现代注释、出版社音频，除非授权明确。
- 不建议只换文本不换产品语言。例如《孙子兵法》不应继续使用“读经、法喜、礼敬”这套佛教语言。
- 不建议把《心经》单独做成一个 app，内容太短，留存需要合集支撑。

## 最终建议

如果目标是最快看到用户反馈：

1. 先做《道德经》：最小内容、最大复用、非佛教破圈。
2. 再做《金刚经 + 心经》：当前用户群最自然扩展。
3. 然后做《论语》：但要先设计译注/学习层，不能只是原文阅读。

如果目标是长期产品线：

先抽象 `BookConfig`，但只抽当前必须的东西，不要提前做复杂书库。抽象完成后，用同一代码库生成多个单书 target，比做一个混杂多书 app 更符合现在的产品气质。

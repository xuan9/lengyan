# 导航与布局审查报告：阅读 / 听经

日期：2026-07-16

> **状态说明（2026-07-18）：历史布局审查快照。** 首页功能区现已定型为四个克制的
> 文字按钮：iPhone 两行排列“续读 + 科判 / 续听 + 搜索”，较宽 iPad 单行排列
> “续读 / 续听 / 搜索 / 科判”，并按内容动态分配续读空间。正文中对旧首页三入口的
> 描述不再代表当前实现；听经页和全局播放体验建议仍属于后续候选，未自动获得实施批准。

## 结论

当前方向是对的：阅读是主入口，听经是第二个 Tab，同时首页、阅读页、通知都能触达听经。这说明产品已经把“听”当成核心能力，而不是附属功能。

但现在还不是最佳状态。主要问题不是播放逻辑，而是导航与布局层级没有完全统一：

- 听经入口很多，但心智不够统一：底部 Tab、首页“续听”、阅读页播放按钮、通知播放都存在。
- 听经页底部播放器与 TabBar 的距离处理仍有硬编码，设备适配风险高。
- 听经小播放器只在听经 Tab 内明显存在，用户在其他 Tab 听音频时缺少“正在听”的全局感知。
- iPad 听经页没有充分利用大屏，列表集中在一列，右侧空间没有承载播放/学习信息。
- 阅读页有两套阅读路径：卷阅读和科判精读；两者的导航按钮、听经按钮、分享收藏入口不完全一致。

我的判断：不建议改 Tab 顺序，也不建议增加新 Tab。应保留「读经 / 听经 / 收藏 / 设置」四 Tab，但要把“听经”从单独页面能力升级为贯穿阅读流程的能力。

## 当前导航结构

真实生效的主导航来自 `AppDelegate.setupTabs`：

- Tab 1：读经，`SutraFrontViewController`
- Tab 2：听经，`ModernAudioPlayerView`
- Tab 3：收藏，`ModernFavoritesView`
- Tab 4：设置，`ModernSettingsView`

代码里还有一个 SwiftUI `ContentView` 的 3 Tab 版本，但实际主界面由 `AppDelegate` 创建 UIKit `UITabBarController`。这部分会增加后续导航重构风险，应当标记为遗留/未来架构，不要让人误以为它是当前入口。

## 做得好的地方

### 1. 听经已经是一级入口

`AppDelegate` 里听经是第二个 Tab，图标用 `headphones`，注释也明确写了“听经是最高优先级的学习方式”。这比把音频藏在设置或阅读页菜单里好。

结论：Tab 层级正确，不需要把听经移到第一位。读经仍应是默认首页，因为它承担总目录、卷章入口、搜索、续读、续听，是全 app 的中枢。

### 2. 首页已经有“开始/续听”

`SutraFrontViewController.setupHeaderView` 里，首页 header 包含：

- 十卷按钮
- 续读/开始读经
- 搜索
- 续听/开始听经

这很好，因为很多用户并不会先点第二个 Tab；首页给出听经入口可以降低启动成本。

### 3. 阅读页右上播放按钮方向正确

`ReaderViewController` 的右上播放按钮和 `AudioManager` 共享下载状态、播放状态和进度圆环。当前逻辑也符合预期：

- 如果正在听当前卷，点击是暂停/继续。
- 如果不是当前卷，点击从当前卷开头开始。
- 下载中显示圆环，防误触。

这对于“边读边听”非常关键，应该保留。

### 4. 听经页有明确的主界面和沉浸模式

`ModernAudioPlayerView` 有列表模式和沉浸模式：

- 列表模式：卷列表 + 底部播放器。
- 沉浸模式：佛画背景 + 竖排标题 + 竖向进度。

这是一个好方向。听经不只是文件列表，而是可以成为独立的沉浸体验。

## 主要问题

### P0：听经底部布局仍有设备适配风险

`ModernAudioPlayerView` 同时使用了真实 TabBar overlap 计算和固定底部 padding：

- 列表内容底部：`audioObserver.showPlayerBar ? 260 : 120`
- 播放器底部：通过 `tabBarOverlapHeight` 补真实重叠高度

这会导致不同设备、不同 TabBar 高度、iPad、iOS 18/26 行为变化时出现不稳定间距。你之前提到的 mini player 与 footer/tabbar 间距问题，本质上就属于这一类。

建议：

- 移除 `260/120` 这种固定内容底部留白。
- 用一个统一的 `AudioPlayerBarMetrics` 或本地计算值：
  - `playerBarHeight`
  - `playerToTabBarGap = 8`
  - `tabBarOverlapHeight`
  - `contentBottomInset = playerBarHeight + playerToTabBarGap + tabBarOverlapHeight + 16`
- 播放器应始终贴近 TabBar 上方，设备差异只由真实测量值决定。

### P0：听经重要，但“正在听”不够全局

现在听经小播放器主要存在于听经 Tab。用户开始播放后切到读经/收藏，底部没有统一的 Now Playing 感知。阅读页右上播放按钮能处理当前卷，但它不是全局播放器：

- 在首页，只能看到“续听”文字。
- 在收藏页，没有明显音频控制。
- 在科判精读页，导航右侧是分享/收藏，不一定有播放。
- 在卷阅读页，有播放按钮，但只针对当前卷。

建议：

- 不要在沉浸阅读正文底部强行放大播放器，会破坏阅读。
- 但可以做一个非常克制的全局“正在听”状态：
  - 首页和收藏页：TabBar 上方显示 36-44pt 的极简正在听条。
  - 正文阅读页：保留右上角圆形播放按钮，不显示底部条。
  - 听经页：继续使用完整播放器。
- 点击全局正在听条进入听经 Tab；按钮只提供暂停/继续。

这样“听很重要”能被感知，同时不压迫阅读。

### P1：首页读/听入口视觉层级仍偏向读

iPhone 首页当前是：

- 续读/开始读经 + 搜索
- 续听/开始听经

如果听经是核心功能，续听不应该像第二行附属项。它应该和续读处于同一层级，只是搜索可以更轻。

建议：

- 首页功能区改成两个同级主行动：
  - 继续读 / 开始读经
  - 继续听 / 开始听经
- 搜索移动为右侧小图标，或保留在标题/工具区域。
- iPad 可以保持三项同行，但听经居中很合理；iPhone 上读/听建议做同级上下两行，而不是读+搜索一行、听单独一行。

### P1：iPad 听经页没有发挥大屏价值

`ModernAudioPlayerView` 使用 `.readingContentWidth()`，iPad 上内容宽度被限制到 680 左右。现有截图里，音频列表占左侧区域，右侧大量留白；底部播放器横跨底部但信息密度不高。

建议 iPad 使用分栏：

- 左栏：卷/咒列表，宽 340-420。
- 右栏：当前播放卡面、进度、播放模式、音频归属、最近听到位置。
- 底部 TabBar 保留；不需要像 iPhone 那样把播放器压在底部。

听经页在 iPad 应该像一个“播放器 + 目录”界面，而不是放大的手机列表。

### P1：两套阅读模式的听经/分享入口不一致

当前有：

- `ReaderViewController`：卷阅读，右上角播放按钮。
- `SutraPageViewController`：分页/叶子阅读，右上角分享 + 收藏。
- `SutraPurePageViewController`：科判精读，右上角分享 + 收藏，左侧返回/目录。

这意味着用户从不同入口进入“阅读”，右上角能力不同。对于“听很重要”的定位，科判精读页如果能推断所属卷，也应提供听经入口，至少在可播放卷内保持一致。

建议：

- 标准化阅读页导航：
  - 左：返回 / 目录
  - 中：标题 + 页码/出处
  - 右：播放优先，分享/收藏收纳到更多或保留两枚较轻图标
- 如果按钮过多，卷阅读保持播放，科判精读可提供“本卷播放”或“进入听经”。
- 不要让“从卷进入”和“从科判进入”像两个不同产品。

### P2：听经页的沉浸模式入口不够自解释

列表播放器右侧当前主要是播放模式按钮。沉浸模式通过 `listButton` 在沉浸控制里返回列表，但从列表进入沉浸模式的入口不够显性；用户可能不知道可以切到佛画模式。

建议：

- 在播放器上加一个明确但克制的“沉浸/展开”图标，例如 `rectangle.expand.vertical` 或 `arrow.up.left.and.arrow.down.right`。
- 沉浸模式里保留清晰的返回列表图标。
- 手势可以保留，但不要只依赖手势。

### P2：TabBar 与沉浸隐藏逻辑较脆

`ModernAudioPlayerView` 通过 `NotificationCenter` 发 `ToggleTabBar`，由 `AppDelegate` 隐藏/显示 TabBar。这个方案能工作，但容易在页面切换、动画中断、未来多窗口时出现状态不一致。

建议：

- 短期保留。
- 如果后续做全局播放器，建议把 TabBar visibility 和 Now Playing 状态集中到一个 app-level coordinator 或 root container，而不是各页面发通知。

## 是否需要调整 Tab 顺序

不建议。

保留：

1. 读经
2. 听经
3. 收藏
4. 设置

理由：

- 读经首页是全 app 的目录和起点，也承载搜索、续读、续听。
- 听经放第二位已经是一级入口，足够高。
- 如果把听经放第一位，新用户会失去“这本经的结构”入口。
- 更好的方式不是换顺序，而是在首页和阅读页把听经入口做强。

## 推荐改版方案

### 第一阶段：修底部布局稳定性

目标：所有设备上播放器都贴近 TabBar，内容不被遮挡。

改动：

- 去掉听经页固定 `260/120` padding。
- 用真实播放器高度 + TabBar overlap 算内容 inset。
- 播放器与 TabBar 统一 8pt 或 10pt gap。
- 对 iPhone SE、普通 iPhone、Pro Max、iPad 都截图验证。

这是最必要的改动。

### 第二阶段：首页读/听同级

目标：用户打开 app 立即知道可以读，也可以听。

改动：

- 首页工具区改为“继续读”和“继续听”两个同级入口。
- 搜索降为轻入口。
- 有进度时显示具体卷/时间；无进度时显示开始读经/开始听经。

### 第三阶段：全局正在听

目标：音频不是只属于听经 Tab。

改动：

- 首页/收藏/设置显示小型正在听条，仅当有当前音频或正在播放时显示。
- 正文阅读页继续用右上播放按钮，不加底部条。
- 点击正在听条进入听经页。

### 第四阶段：iPad 听经分栏

目标：听经页成为真正适合 iPad 的播放器。

改动：

- 左侧曲目列表。
- 右侧当前播放、进度、模式、归属、下载状态。
- 底部播放器在 iPad 可弱化或取消，避免与 TabBar 叠成两层底部控件。

## 最终判断

当前导航不是“差”，而是还没有完全服务“听很重要”这个产品判断。

现在的最佳方向是：

- Tab 结构保持不动。
- 首页强化听经，让读/听同级。
- 听经页底部布局改成动态测量，解决设备间距。
- 阅读页保留并统一本卷播放入口。
- iPad 听经做分栏。
- 后续再考虑全局正在听条。

如果只做一个改动，先做“听经页播放器和 TabBar 的动态布局”。这是最直接影响用户观感和设备适配的点。
